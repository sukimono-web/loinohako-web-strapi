## 1. ゴール

- Strapi 管理画面の `removeChild` クラッシュを **翻訳起因の範囲で根本解消** する
- 修正の正当性を **自動テスト（最小構成）** で恒久的に保証する
- 障害レポート・設計書・実装・テスト・リリースの一連を**他開発者が追跡可能な形**で残す

## 2. スコープ

### IN
- `src/admin/vite.config.js` での HTML 静的注入実装
- 単体テストとビルド成果物検証スクリプト
- ステージング・本番への段階リリース
- 障害レポートの最終更新（クローズ）

### OUT（別チケット）
- ブラウザフロントエンドのエラートラッキング基盤導入（Sentry 等）
- Strapi 5.x 本体アップグレード（対照検証で Strapi 起因と判定された場合は別途起票）

## 6. リスクと意思決定ポイント

| 時点 | 判断 | 分岐 |
|------|------|------|
| T02 完了時 | 対照検証で **翻訳 OFF でもクラッシュ** が出た場合 | 本実装は副作用が小さいので継続するが、Phase 5 と並行して **代替仮説 A（Strapi リグレッション）対応の別チケットを起票** する |
| T10 で再現せず | 仮想 DOM の擬似テストで再現できない場合 | 設計書 §5.4.5 の通り「実翻訳挙動は手動検証に委ねる」スタンスを維持。T14 のステージング検証を厳格化 |
| T14 失敗 | ステージングで対象シナリオが解消しない | 即時 revert。代替仮説の検証へ移行 |

## 7. ロールバック計画

- 単一ファイル新規追加と `package.json` への dev 依存追加のみのため、PR を Revert すれば完全に元に戻る
- データ移行・スキーマ変更を伴わないため、データ整合性リスクなし
